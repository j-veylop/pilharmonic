# Design notes

## Intent

Build a local, inspectable orchestration application inspired by [DeepSeek's super-agent prototype](https://github.com/deepseek-ai/dsh-superagent-prototype), initially running Pi as a subprocess. The first milestone is deliberately small: a person submits work locally, watches it run, and can inspect its outcome. It is not a production implementation of the prototype.

## Reference model

DeepSeek describes incoming source events as triggers grouped into threads. A router evaluates a trigger and can accept, ignore, stop, or defer it; an accepted trigger establishes a ticket and a mandate. Execution assignments are distinct from ticket lifetime. Subsequent thread context is evidence, not authority to expand that mandate. Reports and history allow an operator to see what needs attention. See the upstream [domain model](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md) and [execution design](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md).

## Scope and evolution

The current version has one trusted local source, a deterministic router, a built-in Pi executor and configurable one-shot command executors. Interaction starts at the router: a submitted local request is accepted, assigned and started, with acceptance, assignment and start recorded separately. The router creates one task per request; it does not decompose requests or evaluate them with a model. Each local submission creates a thread, a trigger, an acceptance decision, and a task. A related task can be created in the same thread with its own explicit mandate. A thread follow-up is recorded once and routed to the queued and running tasks in that thread at the time of submission. Thread subscriptions can be paused per task; only subscribed queued and running tasks receive new follow-ups. Pausing does not revoke previously recorded context or in-flight delivery. Resuming does not replay missed inputs. Subscriptions do not include completed tasks or replay earlier follow-ups to later tasks. A trigger retry is idempotent and does not acquire new recipients. Context does not change any mandate. Pi receives the mandate and context together at start. Pi RPC supplies assistant text and tool lifecycle activity to the task output. Running tasks receive follow-ups through RPC; pending, accepted, rejected and unknown delivery states are persisted. Acceptance means Pi acknowledged the command, not that the model consumed it. Its local submission is an explicit request, so deterministic acceptance is sufficient for that source. It does not implement DeepSeek's external sources, authorization policy engine, model-assisted evaluation or routing, automated decomposition, or proactive triggers. Do not treat these omissions as security boundaries. Add sources only alongside explicit authorization, stable trigger identity, idempotent evaluation, and auditable decisions. Keep mandates immutable and distinguish context from authority.

Workspace isolation is opt-in. A queued task can be started in a dedicated Git worktree created from the repository's committed `HEAD`; the source workspace is left untouched and uncommitted files are not copied. The reservation stores an ownership record, is validated before reuse, and is shared by retries of the same task. Worktrees are retained after completion and deletion for manual inspection, and the application never deletes them automatically. Isolation is not a sandbox: the agent still runs on the host with its own permissions. Mixing isolated and shared-workspace tasks against the same repository is allowed but not coordinated beyond Git's own worktree rules. Reviewing or merging isolated changes is manual.

A task's state and history must survive restarts; a process cannot survive an orchestrator restart and interrupted work must be visible. Executor adapters own process invocation and event translation; the router owns decisions and task lifecycle. The UI is a view and control surface, not the source of truth. Each execution is recorded as an attempt with its own status, output and timestamps. Manual retries requeue unsuccessful tasks without changing their mandate; they run in the same workspace and do not roll back prior changes. An isolated task keeps its prepared worktree across retries, so those changes persist too. Concurrency is limited (default two); explicitly started tasks wait in FIFO order when capacity is full and resume after restart. Unstarted drafts stay idle. Structured reports (progress, waiting, blocked, ready, failed) are explicit operator/API observations; free-form Pi output is not automatically interpreted as a report. Reports determine attention stages separately from process status, and reports from an earlier attempt do not govern a new attempt. The local routing policy is fixed and deterministic (`local-1`): it accepts trusted local requests, assigns Pi in the shared workspace and requests execution. The agent registry exposes live-context capability and supports durable executor selection before a manually drafted task is scheduled. The router screen surfaces tasks whose stage needs a person and recent routing decisions. Command executors receive the mandate and queued context on stdin and stream output; only Pi supports live context. Future work should add richer assignments, executor-generated reports, and policy-driven routing before adding external integrations. Avoid assuming that a successful subprocess exit proves the requested work is correct.

## Tool activity

Pi RPC tool events are stored as structured activity, keyed by attempt and tool-call ID. Summaries come from actual command/path/query arguments rather than inferred agent intent. Start, partial-result and end events update a single call; results, status and duration are inspectable in the activity view. Unfinished calls are marked interrupted when the attempt ends or the application recovers after a restart. Storage retains the latest 200 calls per task; argument/result previews are capped at 16 KiB before JSON wrapping, with an explicit truncation marker. Older state files cannot reconstruct arguments or results from earlier plain-text output. One-shot command executors do not emit structured tool activity.

The output transcript is a display of two kinds of content: assistant prose rendered as Markdown, and tool markers rendered as compact status rows with a coloured rail and glyph. Inline markers are a display hint derived from the Pi adapter; the structured activity view is authoritative. A completed call collapses into one row rather than appearing as separate start and finish lines, and agent prose is never interpreted as structured activity.
