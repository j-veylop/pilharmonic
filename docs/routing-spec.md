# Routing and delivery invariants

This is a development specification, not a claim that every feature is implemented. See `design.md` for the current scope.

The deterministic local router and its unified entry point are implemented: trusted local submissions are accepted, assigned and started under policy `local-1`, with separate durable records. Authorization is an explicit gate: a `Policy` receives a normalized request (source, actor, purpose, trigger/thread/parent identity, mandate, workspace and depth) and returns accept, reject or needs-review plus a policy ID and version. The built-in `local` policy (`local-1`) preserves deterministic local acceptance; the separate `subagent` policy (`subagent-1`) covers delegated children. Every task decision records the policy ID/version, source, actor and a versioned SHA-256 digest of the exact input, so a reviewer can recompute what was authorized. Rejected requests create no task and are currently returned as errors rather than persisted as audit records. A dedicated read-only audit export also remains future work. External sources, model-assisted evaluation and a configurable policy engine remain future work.

## Inputs and authority

An input has a stable source identity, trigger ID, thread, timestamp and payload. A retry of the same input must have one durable outcome; a reused ID with different content must fail. Current sources are the trusted local UI and bounded subagent delegation. Before introducing an external source, define how its identity is authenticated, how policy changes affect in-flight work, and how authorization decisions are persisted. Thread membership or a related message alone must never grant authority.

For the trusted local source, the deterministic router accepts a submission and records both an assignment and an execution request; acceptance, assignment and start remain separate records. An explicit accepted request establishes an immutable mandate. A follow-up to subscribed work is contextual input and must not silently expand that mandate. A new task needs its own explicit mandate and decision. Persist the input, decision and all intended deliveries atomically before notifying executors. Delivery to an executor is separate from its acknowledgement and from the agent actually consuming the input; retain unknown outcomes across crashes rather than reporting success. Retries must not create duplicate deliveries to new subscribers that were absent from the original routing decision.

## Scheduling and execution

An explicit start request is distinct from a task that merely exists. A scheduler must enforce its configured concurrency bound even under concurrent starts and completion callbacks. It must never launch work before the relevant state is durable. Running attempts interrupted by a restart are marked interrupted; no process is assumed to have survived. A re-execution must be an explicit, auditable decision and must preserve the mandate and previous attempts. Workspace isolation is the default for new tasks whose source workspace is a Git repository with a committed HEAD: an isolated task runs in a worktree prepared from that commit, with an ownership record validated before reuse. A successful attempt commits pending worktree changes and automatically merges them into the source repository, with merges serialized and conflicts aborted and recorded separately from execution success. Failed and canceled attempts are not merged. Tasks explicitly opted out, tasks in workspaces that cannot be isolated, and tasks created with default isolation disabled still share their workspace. Automatic merging does not replace review, cleanup or recovery rules.

Per-task pause/resume and per-attempt delivery records are implemented: every contextual hand-off retains its trigger, attempt, outcome, reason and timestamps, while the current attempt alone drives the attention stage.

Executor capabilities and adapter-generated structured reports are implemented for the built-in Pi adapter: the registry reports live context, tool activity and structured reports, and Pi records progress/failed observations from its structured lifecycle rather than parsing assistant prose. Command adapters remain one-shot and do not emit reports.

Subagent delegation is implemented as a separate acceptance path (`subagent-1`), not as an expansion of the parent mandate. Agent-initiated requests require a running task with valid, attempt-scoped credentials. The trusted local UI can also delegate from a running parent. The child receives a new trigger, thread and decision, inherits the parent's execution workspace and falls back to its executor when no specialist matches, and is subject to depth and per-parent limits. The control socket is owner-only, request size is bounded, and credentials are never persisted. The spawn and its child are stored before the child starts; failing to start leaves a visible queued child rather than pretending execution began.

## Next milestones

1. Add explicit authorization policies and auditable decisions before introducing external sources. The policy gate and audit evidence exist; policy configuration, rejected-request records and external-source authentication remain open.
2. Extend structured reports to configured command adapters and richer assignment policy; Pi capabilities and adapter reports exist, and explicit operator reports already support waiting, blocked, ready and failed attention states.
3. Extend isolated-worktree handling. Default worktree isolation, automatic merging of successful work, recorded review and worktree cleanup on task deletion exist; explicit discard is available for clean, integrated worktrees. An in-app diff and conflict resolution remain open.
4. Add external sources and model-assisted evaluation only after the deterministic authorization gate; evaluator output is untrusted and cannot authorize itself.

Tests should cover duplicate triggers, subscriber changes during retries, partial or uncertain delivery, process crash, restart, concurrent scheduling, save failure and shutdown. Use fake sources and runners so tests do not need model credentials.
